개요

고지 항목은 법정 공통 항목과 상품별 약관 항목 두 층으로 나눴고, 항목마다 근거 법령과 원문을 붙였습니다. 상담사 음성을 실시간으로 전사하고, 전사가 나올 때마다 체크리스트와 대조해 빠진 항목을 찾습니다.

내가 한 일

무엇을 학습할지부터 결정

팀에서 파인튜닝 이야기가 나왔을 때 대상을 먼저 갈랐습니다. 약관은 개정될 때마다 바뀌고 답변 근거를 추적해야 해서 LLM에 학습시키지 않고 검색해 쓰기로 했고, 도메인 음성이 있는 음성 인식부터 파인튜닝했습니다.

음성 인식 파인튜닝

한국어 Whisper-medium에 LoRA를 붙여 조건과 오류율을 기록하며 11회 학습했습니다. 오류율을 구두점·숫자·띄어쓰기·순수 인식으로 나눠, 실제 인식 오류가 줄었는지를 기준으로 판단했습니다.

서빙 연결

학습한 어댑터를 GPU 서버에 올리고, 봇이 LiveKit 상담 세션의 오디오를 받아 발화 단위 3~5초로 잘라 전사한 뒤 결과를 WebSocket으로 백엔드에 보내게 했습니다. 끊기면 간격을 늘려 가며 재접속합니다.

고지 누락 판정

대화를 구간으로 자르지 않고 전사가 나올 때마다 체크리스트와 대조해 체크와 타임스탬프를 남깁니다. 상태 크기가 고정이라 상담이 길어져도 비용이 늘지 않고, 같은 자료구조를 실시간 경고·영상 표시·동의 목록 세 곳에서 씁니다.

구조

트러블슈팅

TS-01

내가 낸 실험 결론이 틀렸다

상황
네 번째 실험에서 LoRA 용량(rank)을 키워도 오류율이 나아지지 않자 "용량은 병목이 아니다"라고 결론을 적었습니다.
원인을 좁힌 과정
검증 손실 곡선이 학습률이 너무 높을 때의 모양과 닮아 있어서 결론을 다시 의심했습니다. 같은 용량(rank 64, q·k·v·o)에서 학습률을 1e-3에서 2e-4로 낮춘 실험을 따로 돌렸습니다.
해결 · 결과
오류율이 8.09%에서 5.43%로 내려가 결론이 정반대가 됐습니다. 다만 두 실험은 학습 데이터 양과 스케줄러도 달라서, 원인을 학습률 하나로 단정하지 않고 그 차이를 기록에 함께 적었습니다.
배운 점
남이 준 전제보다 방금 내가 적은 결론을 의심하는 쪽이 더 어렵습니다.
TS-02

200건 평가의 1위가 500건에서 밀렸다

상황
200건 평가에서 rank 128 모델(5.38%)이 rank 64 모델(5.43%)보다 좋았습니다. 차이는 0.05%p였습니다.
원인을 좁힌 과정
200건으로 0.05%p 차이를 가를 수 있는지 의심스러워, 최종 후보 4개를 검증셋 전체 500건으로 다시 쟀습니다.
해결 · 결과
5.74% 대 5.56%로 순위가 뒤집혔습니다. 파라미터가 두 배인 모델 대신 rank 64를 최종 채택했습니다.
배운 점
평가 표본의 해상도보다 작은 차이로는 순위를 정하지 않습니다.
TS-03

학습 데이터와 서비스 입력의 음질이 달랐다

상황
학습 데이터는 전화망 8kHz 음성인데 서비스는 브라우저에서 16kHz로 녹음됩니다.
원인을 좁힌 과정
파인튜닝 효과가 그대로 옮겨간다고 가정하지 않았습니다. 서비스와 같은 브라우저 녹음 방식으로 고지 문장 낭독 120건을 모아, 같은 녹음을 파인튜닝 전후 모델에 넣었습니다.
해결 · 결과
오류율이 9.89%에서 4.53%로 내려가 효과가 옮겨간다고 판정했습니다. 대본 낭독은 실제 상담보다 쉬워서 이 숫자는 전이 여부 판정에만 쓰고 절대 성능으로는 쓰지 않았습니다.
배운 점
학습 성능과 서빙 성능은 따로 재야 합니다.
TS-04

증적 영상 표시가 발화보다 늦게 찍혔다

상황
"여기서 고지했음" 표시가 말이 시작된 곳이 아니라 판정이 끝난 곳에 찍혀, 짧으면 2~3초 길면 10초 늦었습니다.
원인을 좁힌 과정
표시 좌표로 판정 완료 시각을 보내고 있었습니다. 발화 시작 위치는 음성 인식 단계에서 이미 계산돼 있었는데 마지막 전송 단계에서 버려지고 있었습니다. 그 값을 되살려도 기준점이 달랐습니다. 하나는 봇이 소리를 받기 시작한 시점, 다른 하나는 녹화 시작 시점부터 잰 값이었습니다.
해결 · 결과
봇이 수신을 시작할 때 실제 시각을 한 번 남겨 두 시계를 맞췄습니다.
배운 점
값이 없어서 생긴 버그가 아니라 있는 값을 버려서 생긴 버그였습니다.
TS-05

부정 표현이 엉뚱한 항목을 체크했다

상황
"지급하지 않습니다" 같은 부정 표현이 해약환급금 항목에 체크로 붙었습니다.
원인을 좁힌 과정
키워드가 판정을 하고 있어서 문장 안의 부정어를 보지 못했습니다.
해결 · 결과
절 단위로 부정 표현을 검사하도록 고쳤습니다. 같은 시나리오에서 잘못 붙은 체크가 14건에서 2건으로 줄었고, 놓친 항목은 0건을 유지했습니다.
배운 점
오탐을 줄이는 수정은 놓침이 늘지 않았는지 같이 봐야 합니다.

결과

항목값조건
문자 오류율11.7% → 5.43%200건 평가 · 검증셋 500건 기준 5.56%
순수 인식 오류7.61% → 4.85%구두점·숫자·띄어쓰기 차이를 뺀 값
처리 속도발화 길이의 0.04~0.16배실제 상담 세션, GPU, 빔 5
판정 오체크14건 → 2건같은 시나리오, 놓친 항목 0건 유지

하지 않기로 한 것

  • 고객 발화 전사 — 병력과 소득이 검색 가능한 텍스트로 쌓입니다. 개인정보 이유로 범위에서 뺐습니다.
  • LLM 파인튜닝 — 약관 개정마다 재학습해야 하고 답변 근거를 추적하기 어렵습니다.
  • QLoRA, large-v3 — GPU 메모리가 충분해 양자화 손실을 감수할 이유가 없었고, 큰 모델은 지연이 늘었습니다.
  • 실제 상담 녹음으로 만든 평가셋은 없습니다. 다시 한다면 표기를 맞춘 오류율을 주지표로 두고, 후보 비교에 신뢰구간을 붙이겠습니다.
