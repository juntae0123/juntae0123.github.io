Hidden Gem

한 문장, 슬라이더, 카드 스와이프로 입력한 취향에 맞는 게임을 17,313개 중에서 찾아줍니다. 기획부터 데이터 구축, 백엔드, 배포, 운영까지 혼자 했습니다.

개요

장르 태그만으로는 같은 RPG라도 느긋한 농장 게임과 어려운 액션 게임을 구분하지 못합니다. 그래서 게임마다 분위기·조작 난이도·사회성 같은 경험 지표(0~10 수치 49개, 불리언 9개)를 만들어 붙이고, 사용자가 문장이나 지표로 말한 취향을 그 지표와 맞춰 봅니다.

내가 한 일

데이터 구축

상위 모델(GPT Batch)이 게임 4,190개를 분석하고, 경량 모델이 12개 예시를 보고 나머지를 채우는 증류 구조를 설계했습니다. 상위 모델에는 개발사와 평점을 가린 입력을 줬습니다.

추천 엔진

LLM이 한국어 취향 문장을 영어 검색 질의와 지표 힌트로 바꾸면, pgvector HNSW로 찾은 임베딩 유사도에 지표 점수를 더해 순위를 냅니다.

백엔드

추천·검색 읽기 경로는 FastAPI, 인증·회원·관리자는 Django로 나눴습니다. 같은 DB를 쓰기 때문에 스키마 정본을 SQLAlchemy 모델 하나로 정해 마이그레이션 충돌을 막았습니다.

운영 자동화

주 1회 파이프라인(신작 수집 → 배치 분석 → 적재 → 임베딩 → 리뷰 갱신 → 발굴 지수)을 돌리고 단계마다 Discord로 알립니다. OpenAI 비용이 일 $50, 시간당 $5를 넘으면 호출을 막습니다.

측정 도구

고정 질의 19개를 운영 API에 던져 상위 10개를 저장하고 이전 회차와 비교하는 스냅샷 도구를 만들어, 채점 로직을 바꿀 때마다 전후를 쟀습니다.

보안 점검

무인증이던 운영 캐시 삭제 엔드포인트에 토큰을 걸고, 토큰이 없으면 막히도록(fail closed) 했습니다. 정의만 되어 있던 레이트 리밋을 실제 검색 경로에 붙였습니다.

트러블슈팅

TS-01

사용자 취향 대신 상수 5.0과 비교하던 채점 함수

상황
점수 구조를 문서로 정리해 다른 AI 모델로 외부 검토를 네 차례 받았고, 캐시 오염과 분모 오류는 거기서 잡았습니다. 검토는 전부 문서를 대상으로 했고, 채점 함수 원문을 놓고 본 적은 없었습니다.
원인을 좁힌 과정
채점 함수 원문을 읽었습니다. 호출하는 쪽은 사용자가 움직인 지표 3~5개만 넘기는데, 함수는 빠진 지표를 기본값 5.0으로 채우고 있었습니다. 핵심 점수의 65%를 차지하는 장르 지표가 취향이 아니라 상수 5.0과 비교되고 있던 겁니다. 힐링 취향을 9로 넣어 보니 해당 지표가 전부 5인 게임이 66.1점, 전부 9인 게임이 50.0점으로 뒤집혀 나왔습니다.
해결 · 결과
사용자가 지정한 지표만 채점하는 새 채점 버전을 플래그로 분리해 넣고, 스냅샷 도구로 전후를 비교한 뒤 운영에 적용했습니다.
배운 점
문서 검토는 문서에 적힌 것만 검사합니다. 함수 기본값처럼 문서에 없는 동작은 소스를 열어야 보입니다.
TS-02

회차마다 바뀌던, 취향 채점과 무관한 검색 결과

상황
채점을 바꾼 뒤 "취향 채점 함수를 거치지 않는 문장 검색 경로는 상위 10개가 그대로여야 한다"를 미리 기준으로 정해 뒀는데, 그중 하나가 10개 중 9개만 일치했습니다.
원인을 좁힌 과정
채점 결함을 먼저 의심했지만 이전 회차 기록을 보니 같은 두 게임이 반대로 뒤집혀 있었습니다. 채점이 아니라 질의를 분석하는 LLM 출력이 회차마다 조금씩 흔들려 10위 경계가 바뀐 것이었습니다.
해결 · 결과
질의 분석 결과를 7일간 캐시해 측정 잡음과 LLM 호출 비용을 함께 줄였습니다.
배운 점
바꾸기 전에 바뀌면 안 되는 것부터 정해 두지 않았다면 이 변동을 채점 결함으로 읽었을 겁니다.
TS-03

서비스 장애를 놓친 헬스체크

상황
같은 날 두 번, 랭킹이 전부 500 오류를 내고 캐시가 전멸했는데 상태 점검 주소는 정상이라고 답했습니다.
원인을 좁힌 과정
상태 점검이 내부를 확인하지 않고 고정 문자열만 돌려주고 있었습니다. 두 장애의 원인은 같았습니다. 플랫폼에서 DB 비밀번호가 바뀌어도, 이미 떠 있던 컨테이너는 옛 값을 들고 있었습니다.
해결 · 결과
점검이 DB에 SELECT 1, Redis에 PING을 실제로 보내고 실패한 쪽과 사유를 돌려주게 바꿨습니다. 이 점검이 다음 Redis 인증 실패를 처음 잡았습니다. 비밀값 교체 절차 마지막에 의존 서비스 재배포와 실제 조회 확인을 넣었습니다.
배운 점
무엇을 확인하는지 모르는 헬스체크는 증거가 되지 않습니다.
TS-04

반년 동안 초기 상태로 남은 운영 DB

상황
운영에서 발굴 지수를 계산하려고 미리보기를 돌리니 리뷰 정보가 없는 게임이 4,193개로 나왔습니다. 운영 DB가 초기 데이터 그대로였고, 이후 수집한 게임은 운영에 하나도 없었습니다.
원인을 좁힌 과정
파이프라인 설정을 따라가 보니 적재 대상이 운영이 아니라 로컬 DB였습니다. 문서에는 운영에 적재한다고 적혀 있었습니다. 첫 동기화를 돌리자 이번에는 운영 Postgres가 재시작을 반복했는데, 데이터가 아니라 WAL 파일이 작은 볼륨을 먼저 채운 것이었습니다.
해결 · 결과
볼륨을 늘려 복구하고, 삭제 없이 upsert만 하는 동기화 도구를 만들어 당시 운영 DB 전체인 12,843행 기준 61분 걸리던 작업을 85초로 줄였습니다. 운영 랭킹이 로컬 스냅샷과 같은지 운영 API로 확인했고, 대량 쓰기 전 용량을 확인하는 규칙을 추가했습니다.
배운 점
"설정을 바꿨다"와 "운영이 바뀌었다"는 다른 사건입니다. 변경 뒤에는 운영에서 직접 확인합니다.

버린 것과 남은 것

  • LLM이 매긴 "숨은 명작" 점수는 리뷰 실측과 상관이 거의 없어 버리고, 리뷰 수와 긍정률로 계산하는 지수로 바꿨습니다.
  • 사용자는 아직 적습니다 — 행동 로그 기준(2026-05-25~, 익명 브라우저 ID) 방문 브라우저 120, 검색 26, 결과 클릭 29, 가입 5, 이틀 이상 다시 온 브라우저 2. 응답 지연 p95는 아직 재지 않았습니다.
